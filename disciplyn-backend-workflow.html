PRODUCT WORKFLOW · BACKEND VISION
FROM FRONTEND DEMO TO REAL SERVICE

What happens behind
the discipline.

This is the intended end-to-end workflow if Ravion were connected to production services: how a trader signs in, grants broker access, answers the check-in, gets a behaviour profile, and reflects with Consult. It is a design/specification document only; no backend has been built.

Important distinction: the current prototype is frontend-only. Broker sign-in is simulated, profile metrics/trades are sample data, questionnaire/chat state is browser-local, and Consult uses canned responses. The workflow below describes the real service that would replace those demo behaviours.
01 / THE TRADER JOURNEY

One connected loop

The product should move from permission → context → insight → reflection, without placing trades or taking control of the brokerage account.

01 · ACCESS

Choose broker

Trader chooses Zerodha, Groww, Dhan, etc. Explain requested data access and purpose.

02 · AUTHORIZE

Broker consent

Redirect to the broker’s real authorization screen. Trader approves read-only access.

03 · PROFILE

Identify user

Backend validates the OAuth return, securely stores the session and checks onboarding status.

04 · CHECK-IN

Ask 7 questions

New user gets one randomly assigned questionnaire set; answers save as they progress.

05 · SYNC

Import trades

With consent, sync permitted trade/order history and normalize it into a common ledger.

06 · INSIGHT

Build profile

Compute behaviour signals, performance metrics, trends and evidence-linked flags.

07 · REFLECT

Consult

Trader asks about a pattern; the assistant uses approved profile context to suggest a safe experiment.

02 / FIRST VISIT VS RETURNING VISIT

Two paths after authorization

NEW TRADER

Consent → check-in → first insights

After broker identity is verified, create the app profile and assign a questionnaire set. The server stores the set version and each answer. If there is no broker connection or the trader skips trade import, onboarding still completes with clearly labelled limited insights.

Create profileAssign random set 1–5Save answer per questionSync then calculate
RETURNING TRADER

Consent refresh → sync delta → dashboard

Recognize the account from the secure app session, check that the broker connection remains valid, and fetch only new/changed data since the last successful sync. Return the latest profile snapshot without asking the same onboarding questions again.

Validate sessionRefresh broker grantSync deltaRefresh insights
OAuth detail: the broker handles the trader’s password and any MFA. Ravion should never collect broker passwords. Use an OAuth state/CSRF check and PKCE where the broker supports it; exchange authorization codes server-side and keep access/refresh tokens out of browser storage.
03 / WHAT THE BACKEND DOES

Behind the loading state

Trade ingestion and normalization

  • Use a separate adapter for each broker; each returns different names, timestamps, fees, order states and instruments.
  • Convert completed fills into a canonical execution ledger. Group partial fills into positions/trades carefully; handle intraday, delivery, F&O, corporate actions, charges, timezone and market holidays.
  • Deduplicate by broker execution ID; retain source IDs and sync timestamps for audit/debug.
  • Backfill only what the broker makes available. Show the date range and freshness; never imply incomplete data is complete.

Signals with explainable evidence

  • Rules identify candidate patterns: stop moved after entry, larger size after a loss, fast re-entry, late chase, or exits that miss a planned target.
  • Each flag stores the rule/version, source trade IDs, timestamps, confidence, and a short factual reason.
  • Cost estimates should be labelled estimates and use a documented comparison method (e.g. original planned risk vs realized result). Avoid presenting a counterfactual as certain money lost.
  • Score changes are based on consistent, versioned rules and enough observations—not a diagnosis or a prediction of returns.
04 / CONSULT REQUEST LIFECYCLE

Ground the conversation, keep it private

When a trader sends a message

  1. Browser sends the message plus a conversation ID to the authenticated API.
  2. Server checks ownership and permission, then fetches only relevant profile facts and selected flagged trades.
  3. A prompt composer asks the LLM to explain patterns with citations to trade IDs/date ranges, ask a useful follow-up, and offer a small behavioural experiment.
  4. Stream the response to the app. Save conversation and any user-approved goal; do not silently write to the broker or make orders.

Safety and user control

  • Present as reflection/education, not personalized financial advice, guaranteed outcomes, or trade instructions.
  • Keep model output grounded in the trader’s data and disclose when data is missing or uncertain.
  • Give the trader controls for chat history retention/deletion and whether their profile context may be used.
  • Never send broker tokens or unnecessary personal data to the model. Review provider retention and training settings before launch.

06 / DATA THAT WOULD BE STORED

Keep the model small and traceable

Trader & session

App user ID, display preferences, secure session reference, consent/retention settings.

BrokerConnection

Broker name, encrypted token reference, granted scopes, account alias, expiry, last sync, revocation status.

QuestionnaireResponse

Set/version, question ID, answer, timestamp, and consent/context. Do not store more than needed.

Execution / Trade

Canonical symbol/exchange, side, quantity, price, fees, timestamps, source IDs and sync provenance.

BehaviourFlag

Tag, severity/confidence, rule version, evidence trade IDs, explanation and observed period.

ProfileSnapshot

Score, P&L metrics, trend points, coverage window and calculation version/as-of time.

Goal & progress

Trader-selected target, start/end, progress rule, events counted, completion/badge state.

ConsultConversation

Messages, user consent, relevant context references, retention expiry and deletion state.

SyncJob & audit

Job state, source, time range, retries/errors and security-sensitive access events.

07 / TRUST BOUNDARIES

What must be true before real launch

Broker credentials stay at broker

OAuth only. Encrypt broker tokens server-side with managed keys; never expose them in API responses or localStorage.

Private data is per-user

Authorize every read/write by user and account ownership. Use least privilege, audit access, rate limit, and test tenant isolation.

Consent is specific & revocable

Separate consent for broker sync, analytics, chat context and push notifications. Make disconnect and deletion discoverable.

Respect Indian privacy rules

Design data notices, purpose limitation, retention, grievance/contact and deletion flows for applicable Indian privacy law; obtain qualified legal review.

No order placement

Read-only integration for this product. Avoid any action that could submit, modify, or cancel a market order.

Push is opt-in

Ask permission only after explaining the nudge. Store push subscriptions securely; let the trader pause/withdraw at any time.

Proposed deployment shape: keep the existing static Next.js PWA on Cloudflare Pages; add authenticated API endpoints on a Cloudflare Worker (or another suitable backend), a relational database for user/trade/profile records, encrypted secret storage for broker tokens, and a queue for sync/score jobs. Use a model provider only behind the server. This is an architecture suggestion—not a committed provider choice.
08 / REPLACE THE DEMO IN THIS ORDER

Practical implementation sequence

Foundation

1. User/session model and secure sign-in.
2. Broker consent for one broker; read-only authorization.
3. Questionnaire assignment + answer persistence.
4. Trade sync job, canonical schema and clear sync coverage.

Insights & controls

5. Validate metric definitions and rule signals on test data.
6. Profile APIs and empty/loading/partial-data states.
7. Consult with consent, grounded context and streaming.
8. Goals, push opt-in, disconnect/export/delete; security and privacy review.
